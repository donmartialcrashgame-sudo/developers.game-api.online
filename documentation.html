01 · INTRODUCTION

Welcome to Game API

Game API is a developer platform for integrating game-related services into websites, applications and backend systems. The platform is designed around authenticated API access, API-key management, game data and real-time communication.

This public documentation explains the concepts you need before you start. Account-specific controls, private credentials and detailed developer-console workflows are available after you sign in.

Architecture principleFor production applications, keep your secret API credential on your backend. Your frontend should normally communicate with your backend rather than exposing a production secret in browser code.

What you can build

  • Game dashboards and monitoring interfaces.
  • Applications that consume crash-game information.
  • Real-time game displays powered by WebSocket events.
  • Backend services that collect and process game data.
  • Internal developer tools that monitor API usage.
02 · QUICKSTART

Make your first integration

The normal integration flow is simple: create an account, create an API key, store it securely, authenticate requests, read the response and then build your application around the documented response contract.

Step 1 — Create an account

Create your Game API developer account and complete the available email verification/security steps.

Step 2 — Create an API key

Open the developer console, go to API Keys and create a credential with a descriptive name.

Step 3 — Store the secret

Save the secret in a server-side environment variable or secret manager. Never commit it to source control.

Step 4 — Authenticate

Authorization: Bearer YOUR_API_KEY

Step 5 — Handle the response

Check the HTTP status before using the response body. Treat error responses as part of the API contract rather than assuming every request succeeds.

03 · AUTHENTICATION

Authentication

Game API integrations use credentials to associate requests with an authorized developer account or application. The exact credential required depends on the service you are calling.

Developer ConsoleSupabase Auth session used for account access and console features.
API integrationUse the API credential required by the target API route.
Real-time serviceAuthenticate the WebSocket connection using the current service protocol.
ImportantA browser session token and an application API secret are different credentials. Do not copy a user session token into code as if it were a permanent API key.
04 · CREDENTIALS

API keys

API keys identify your application when using protected Game API services. The developer console provides the interface for creating, reviewing and revoking your keys.

CreateIssue a new key for an application, environment or service.
UseSend the credential in the authentication format required by the endpoint.
RotateReplace an old credential with a new one when needed.
RevokeDisable a credential that is exposed, retired or no longer needed.

Naming recommendation

Use clear names such as Production Backend, Staging, Mobile App or Testing. Good names make credential rotation and incident response easier.

05 · HTTP

HTTP requests

Use HTTPS for production requests. Send JSON headers when the endpoint expects JSON and always inspect the HTTP response status.

GEThttps://api.game-api.online/...
const response = await fetch("https://api.game-api.online/your-endpoint", {
  method: "GET",
  headers: {
    "Accept": "application/json",
    "Authorization": "Bearer YOUR_API_KEY"
  }
});

const data = await response.json();

if (!response.ok) {
  throw new Error(data.error || data.message || "Game API request failed");
}

Server-side example

curl -X GET "https://api.game-api.online/your-endpoint" \
  -H "Accept: application/json" \
  -H "Authorization: Bearer YOUR_API_KEY"

Use the exact endpoint path, authentication scheme and parameters published for the service you are integrating.

06 · RESPONSES

Read responses defensively

Do not assume every successful response contains every optional field. Preserve forward compatibility by ignoring fields your client does not recognize and validating fields your application depends on.

{
  "success": true,
  "data": [],
  "count": 0
}

Good client behavior

  • Check response.ok or the HTTP status.
  • Parse JSON only when the response content is JSON.
  • Validate required fields before using them.
  • Log request IDs or safe diagnostic information when supplied.
  • Never log authorization headers or complete API secrets.
07 · ERRORS

Error handling

Build error handling into the integration from the beginning. Authentication, permission, rate-limit and server errors require different responses from your application.

400Review the request parameters, body or required fields.
401Check the credential, session, expiration and revocation state.
403Check access, plan and permissions for the requested resource.
404Confirm the endpoint path and resource identifier.
429Reduce request frequency and apply retry/backoff behavior.
5xxRetry safely with backoff and check platform status.
08 · CRASH GAME

Crash-game data

The crash game operates through live rounds. A round can move through a betting phase, a running phase and a crash state. Applications should consume the server's state rather than trying to control the game lifecycle from a client.

Example status message

{
  "type": "crash_status",
  "status": "crash",
  "round_number": 125,
  "multiplier": "3.47",
  "crashed_at": "2026-09-24T08:00:00Z"
}

Clients should tolerate additional fields and should not hard-code a particular round number, multiplier or timestamp. Use the current event/data contract supplied by the API service.

Real-time firstIf your interface needs continuously changing game state, use the supported real-time connection rather than repeatedly polling at a high frequency.
09 · REAL TIME

WebSocket

Game API provides a real-time WebSocket endpoint for integrations that need live events:

wss://api.game-api.online/realtime

Connection lifecycle

  1. Open the WebSocket connection.
  2. Wait for the server connection response.
  3. Authenticate using the current WebSocket authentication protocol.
  4. Listen for supported events.
  5. Update your application state from server events.
  6. Reconnect after unexpected disconnects with exponential backoff.

Connection response

{
  "type": "connected",
  "service": "game-api-websocket",
  "authenticated": false,
  "protocol": "1.0"
}

An unauthenticated connection response does not mean that protected game events are available. Complete the authentication handshake required by the service.

10 · USAGE

Usage and limits

API usage is associated with the credentials making requests. Your available request allowance and active-key limits depend on the plan attached to your account and can change as the platform evolves.

Do not hard-code plan limits into your application as permanent constants. Prefer current API responses and developer-console information when displaying quotas.

EfficiencyCache safe data and avoid unnecessary repeated requests.
PollingUse reasonable intervals; prefer real-time events when supported.
RetriesUse bounded exponential backoff and avoid retry storms.
MonitoringTrack request volume, errors and credential activity.
11 · SECURITY

Security best practices

  • Never publish a production API secret in frontend source code.
  • Keep secrets in environment variables or a managed secret store.
  • Use separate credentials for production and testing.
  • Rotate exposed credentials immediately.
  • Never include Authorization headers in application logs.
  • Use HTTPS for all production HTTP traffic.
  • Protect the developer account with MFA/TOTP or passkeys where available.
  • Review and revoke unused API keys.
  • Restrict internal access to production credentials.
Credential exposed?Open the developer console, revoke the affected key and create a replacement. Do not continue using an exposed credential just because it still works.
12 · PRODUCTION

Production integration guide

Application architecture

A common production design is client → your backend → Game API. Your backend stores the secret, authenticates with Game API and exposes only the data your client needs.

Reliability

Use timeouts, bounded retries, exponential backoff, connection-health checks and graceful WebSocket reconnection. Keep the last known valid state when appropriate, but make it clear to users when data is stale.

Observability

Record safe operational information such as status codes, latency and internal request identifiers. Never record complete secrets or authentication headers.

Deployment checklist

  • Production credentials are stored as secrets.
  • HTTPS is enabled.
  • Errors are handled without exposing internal credentials.
  • WebSocket reconnect logic is tested.
  • Rate limits and usage are monitored.
  • Credential rotation has been tested.
  • A support process exists for incidents.
13 · FAQ

Frequently asked questions

Where do I create an API key?

Sign in to the Game API developer console and open API Keys.

Can I put my API key in JavaScript?

For a production secret, avoid exposing it in browser code. Use your backend as the secure boundary.

How do I connect to real-time events?

Use the WebSocket endpoint wss://api.game-api.online/realtime and follow the current authentication/handshake requirements.

What should I do if a key is exposed?

Revoke it immediately and issue a replacement. Then review where the secret was exposed and remove it from source history or logs where appropriate.

Where is the detailed developer reference?

Sign in to the developer console and open Private Documentation for authenticated integration guidance.
